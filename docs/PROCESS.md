# Процесс работы над проектом

> Last reviewed: 2026-07-24

> Как ведётся разработка: ветки, PR, ревью, тесты, отчётность. Состояние проекта
> (что сделано / что проверить) — в [`project-map.md`](project-map.md); технический
> гайд — в [`../CLAUDE.md`](../CLAUDE.md).

## Ветки, PR, merge

- В `main` **напрямую не пушим**. Любая работа — в отдельной ветке, изменения
  вливаются через **Pull Request** (описание на русском: что / зачем / на что влияет).
- **Один PR — одна логическая задача.** Не смешиваем несвязанные изменения.
- **Мержит владелец** — сам, по явному сигналу. Автомерж/force-merge не используем;
  **PR не мержится без явного сигнала владельца.**
- **Не трогаем без сигнала владельца:** деплой-триггеры (`on:` в workflow'ах),
  прод-образ, решение №0 (контур деплоя), выдачу секретов.
- После смерженного PR **синхронно обновляем `docs/`** — документация не отстаёт
  от состояния (в первую очередь [`project-map.md`](project-map.md)).

## Ревью — 5 проверяющих

Перед мержем содержательных изменений привлекаем `/review` **+ параллельно 5 ролей**
(модель Sonnet; предупреждаем, что проект большой — не падать по таймауту):

1. **Документация / Skill** — оценка доков и файлов навыков, синхронизация.
2. **Программист** — адекватность решений, JSDoc, типизация TS, корректность.
3. **Тестировщик** — покрытие тестами и сами тесты.
4. **Безопасность** — отдел ИБ (уязвимости, санитайзер, CSP, секреты).
5. **Тех-директор** — общая инженерная оценка, скоуп, вердикт.

Отчёт о проверке — на русском, кратко по формату **кто · что · почему · как исправить**
с пометкой важности (blocker/major/minor/nit). Замечания устраняем **в этом же PR**;
вынос в отдельный issue/PR — только по согласованию.

**Пропорциональность.** Полный проход 5 ролей — на содержательные/рисковые изменения
(код, security-overrides, поведение конвертера, деплой-pipeline). Для рутинных
патч/минор-бампов зависимостей, которые CI-гейт проверяет полностью (build+e2e+test),
достаточно тщательного само-ревью + зелёного CI.

## Тесты и штамп ревью

Конвенции кода — в [`../CLAUDE.md`](../CLAUDE.md) § Conventions (там же авторитетный
список converter-утилит, требующих тестов, и правило штампа `> Last reviewed:`).
Процессная сторона:

- **Тесты** обязательны для правок converter-утилит; перед коммитом — полный гейт
  `pnpm check` (= lint + typecheck + test). Полный план проверок и портальный
  QA-чеклист — в [`project-map.md`](project-map.md) § «Что проверить».
- **Штамп** `> Last reviewed: YYYY-MM-DD` бампим **только** при содержательном
  изменении дока (проверяет `tests/mdReviewStamp.test.ts`; reporting-kit и
  `tests/`-фикстуры исключены).
- **Перед коммитом доков** прогоняем всё, что CI гоняет в `docs-links.yml`:
  `bash scripts/check-docs.sh && bash scripts/check-skills.sh && bash scripts/check-tg.sh`.

## Отчётность в Telegram (reporting-kit)

Вендорный бандл для работы с AI-агентом и отчётов в Telegram лежит в
[`reports/`](reports/) (зеркалит `.claude/skills/*`). Держим **как есть**, чтобы
синхронизировать с источником (`bx-shef/ai-agent`); у него свои конвенции и свой CI,
поэтому он исключён из наших проверок (`mdReviewStamp`, ESLint).

- Навыки/команды готовят текст отчёта: `/report-status` (срез по `project-map.md`),
  `/report-digest` (дайджест по репозиториям за период), `/report-questions`
  (вопросник заказчику по § «Открытые вопросы»).
- Отправляет **только** `scripts/tg-send.sh` и **только по явной команде «шли»** —
  не раньше. Без `TG_BOT_TOKEN`/`TG_CHAT_ID` скрипт намеренно отказывает. Секреты —
  в `.env` (в git не коммитим).
- Промпты в `reports/` — **канон**; тела `.claude/skills/*/SKILL.md` — их зеркало.
  При правке промпта синхронно обновляем `SKILL.md` (и наоборот); идентичность
  проверяет `scripts/check-skills.sh` и CI (`docs-links.yml`).

## Bitrix24 через хук

Для setup/проверки портала используем входящий вебхук `B24_HOOK___SUFFIX` (свой
суффикс под портал). Хук с максимальными правами — **секрет**: храним в окружении/
секретах, не в git/логах; для рантайма — отдельный хук с минимальными правами.
