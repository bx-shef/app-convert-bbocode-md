# Процесс: от настроек до данных в Bitrix24

> Last reviewed: 2026-07-28

Один сквозной путь: настроить → собрать → выложить → подключить к Bitrix24 →
работать с данными портала. Шаги идут по порядку, каждый можно проверить.

Соседние документы: [карта проекта](project-map.md) — что готово, а что нет;
[планы](ROADMAP.md) — что будет потом.

---

## Шаг 0. Что нужно приготовить

| Что | Зачем | Обязательно |
|---|---|---|
| Домен с HTTPS | Bitrix24 пускает в окно внутри портала (iframe) только по `https` | да |
| Сервер с Docker | основной способ размещения | да (GitHub Pages — только витрина) |
| Портал Bitrix24 с правами администратора | зарегистрировать приложение | да |
| Доступ к репозиторию на GitHub | сборка и выкладка идут через GitHub Actions | да |

### Защита главной ветки — настроить один раз

Иначе изменения с непройденными проверками можно влить в `main` вручную, и
дальше они уедут в прод. Настраивается руками в GitHub:
**Settings → Branches → Add branch protection rule**, шаблон ветки `main`:

- Require a pull request before merging (запретить прямые записи в `main`);
- Require approvals — минимум 1;
- Require status checks to pass → выбрать проверку **`ci`**;
- Require branches to be up to date before merging;
- Require conversation resolution before merging;
- Block force pushes и Restrict deletions;
- Do not allow bypassing the above settings.

Проверка шага: домен открывается по `https`, на сервере работает
`docker compose version`, а попытка влить PR с красными проверками блокируется.

## Шаг 1. Настройки приложения

Настройки задаются переменными окружения. Они **попадают внутрь сборки** — то
есть поменять их «на лету» нельзя, после изменения нужно пересобрать приложение.

### Обязательная

| Переменная | Что это | Пример |
|---|---|---|
| `NUXT_PUBLIC_SITE_URL` | публичный адрес приложения, без слэша в конце | `https://convert.example.com` |

### Необязательные — каждая включает свою функцию

Пустое значение = функция выключена. Это сделано намеренно: пока значение не
задано, ничего лишнего не грузится и не показывается.

| Переменная | Что включает | Где взять значение |
|---|---|---|
| `NUXT_PUBLIC_YANDEX_COUNTER_ID` | счётчик посещений на публичной странице (внутри портала не работает намеренно) | номер счётчика в Яндекс.Метрике |
| `NUXT_PUBLIC_FEEDBACK_URL` | кнопку «Сообщить об ошибке конвертации» | адрес вашего внешнего обработчика (он должен сам принимать запросы из браузера и ограничивать частоту обращений — требования расписаны в `.env.example`) |
| `NUXT_PUBLIC_MARKETPLACE_SLUG` | предложение оценить приложение (только внутри портала) | код приложения в Маркете Bitrix24 |
| `NUXT_ALLOWED_HOSTS` | доступ к dev-серверу через туннель (только для разработки, в готовое приложение не попадает) | домен вашего ngrok или cloudflared |
| `NUXT_APP_BASE_URL` | размещение в подпапке домена вместо корня | по умолчанию `/`; менять только если приложение живёт не в корне |

Ни одна из этих переменных не секрет: те, что начинаются с `NUXT_PUBLIC_`, видны
в коде страницы по замыслу, остальные — настройки сборки и разработки.
**Секреты в приложение не кладутся никогда.** Токен обработчика обратной связи
живёт на стороне обработчика, ключи Telegram — в окружении, не в репозитории.

Где прописывать значения:
- **сборка вручную** — файл `.env` рядом с проектом (образец — `.env.example`);
- **сборка через GitHub Actions** — «Settings → Secrets and variables → Actions → Variables»;
- **работа контейнера на сервере** — файл `.env.prod` (домен, почта для сертификата, версия образа).

Проверка шага: команда `pnpm build` проходит без ошибок.

## Шаг 2. Сборка и выкладка

Основной способ — **Docker-образ на своём сервере**. GitHub Pages используется
только как публичная витрина: там нет серверных заголовков безопасности.

### Как это происходит

1. Изменения попадают в ветку `main`.
2. GitHub прогоняет проверки: линтер, типы, тесты, сборку и проверку интерфейса.
3. **Только если все проверки зелёные** — собирается образ и выкладывается в реестр GHCR.
   Красная сборка в прод не уезжает: это правило зашито в настройки выкладки.
4. Образ помечается двумя метками: `latest` и точный номер сборки (`:<номер коммита>`) —
   вторая нужна для отката.

Ручной запуск выкладки (кнопка «Run workflow» в GitHub Actions) проверки обходит —
он оставлен для аварийных случаев и отката.

### Обновление на сервере

```bash
make prod-redeploy   # забрать новый образ, перезапустить, проверить работоспособность
```

### Откат на прошлую версию

```bash
make prod-rollback TAG=<номер коммита>
```

Откат **разовый**: следующий обычный `make up` вернёт версию `latest`. Чтобы
закрепить откат, пропишите `DOCKER_TAG=<номер коммита>` в `.env.prod`.

### Проверка после выкладки

```bash
make prod-smoke                       # приложение внутри контейнера отвечает
scripts/smoke.sh https://ваш-домен    # снаружи: страница открывается, заголовки на месте
```

### Если нужно собрать вручную

Обычно не требуется — сборкой занимается GitHub. Но если GitHub Actions
недоступен или нужно проверить образ до отправки изменений:

```bash
NUXT_PUBLIC_SITE_URL=https://ваш-домен \
DOCKER_IMAGE=ghcr.io/bx-shef/app-convert-bbocode-md \
DOCKER_TAG=latest \
pnpm run deploy docker --push        # без --push соберёт локально, никуда не отправит

pnpm run deploy gh-pages             # собрать вариант для витрины
```

Проверить собранный образ на своей машине, не трогая сервер:

```bash
HTTP_PORT=8080 docker compose up -d  # откроется на http://localhost:8080
```

Проверка шага: `https://ваш-домен` открывает конвертер, в адресной строке замок.

## Шаг 3. Регистрация приложения в Bitrix24

В портале: **«Разработчикам» → «Иное» → «Локальное приложение»**.

| Поле | Что вписать |
|---|---|
| Application URL | `https://ваш-домен` |
| Installation URL | `https://ваш-домен/install` |
| Назначение | приложение в iframe |
| Права (скоупы) | `user_brief`, `im`, `placement`, `task`, `crm`, `log` |

Зачем нужны права: `im` — вставка текста в чат; `task`, `crm`, `log` — чтение и
запись описаний задач, комментариев CRM и постов Ленты; `placement` — размещение
кнопки в интерфейсе портала; `user_brief` — определить язык интерфейса.

Проверка шага: приложение сохранено, в его карточке появилась кнопка «Установить».

## Шаг 4. Установка в портал

Нажмите **«Установить»**. Портал откроет страницу `/install`, которая:

1. соединится с порталом,
2. зарегистрирует кнопку конвертера над полем ввода чата,
3. покажет «Готово!».

После этого у поля ввода чата появляется кнопка **BBCode** — по нажатию
открывается конвертер прямо в чате.

**Сменили домен или пересобрали с другим адресом?** Откройте `/install` ещё раз:
страница сама отвяжет старый адрес и привяжет новый.

Проверка шага: в чате портала есть кнопка BBCode, по нажатию открывается окно конвертера.

## Шаг 5. Работа с данными портала

Ради этого всё и делалось. Два сценария.

### Текст в чат

1. Нажмите кнопку **BBCode** у поля ввода чата.
2. Нажмите **«Загрузить»** — то, что уже написано в поле ввода, появится в редакторе в удобном виде (Markdown).
3. Отредактируйте текст.
4. Нажмите **«Вставить»** — текст вернётся в поле ввода чата в формате Bitrix24.

### Описания задач, комментарии CRM, посты Ленты

На главной странице конвертера есть панель работы с порталом:

1. Выберите тип объекта: **Задача**, **Комментарий CRM** или **Пост Ленты**.
2. Впишите номер объекта (ID).
3. Нажмите **«Загрузить»** — текст объекта появится в редакторе.
4. Отредактируйте.
5. Нажмите **«Сохранить»** — текст запишется обратно в портал.

Что важно знать:
- **Сохранение перезаписывает текст объекта целиком.** Проверяйте номер объекта перед нажатием.
- Вне портала (если открыть конвертер как обычный сайт) кнопки показывают предупреждение и ничего не отправляют — это защита от случайных действий.
- Если портал не ответил за минуту, появится сообщение об этом. Повторите попытку.

Проверка шага: загрузили описание тестовой задачи, изменили, сохранили — в портале виден новый текст.

## Если что-то пошло не так

| Что видно | Причина | Что делать |
|---|---|---|
| Белый экран внутри портала | приложение отдаётся по `http` — Bitrix24 не пускает такое в окно портала | включите `https`. (Ограничение на список доменов в заголовках сервера пока в режиме наблюдения и белый экран не вызывает — но домен портала лучше прописать заранее, до включения боевого режима) |
| Кнопка в чате не появилась | установка не дошла до конца | откройте `/install` ещё раз и дождитесь «Готово!» |
| Кнопка есть, но открывается пустое окно | адрес приложения сменился, привязка устарела | откройте `/install` — он перепривяжет адрес |
| «Не удалось загрузить» или «Не удалось сохранить» | неверный номер объекта либо не хватает прав | проверьте номер и тип объекта; права — в карточке приложения |
| «Bitrix24 не ответил вовремя» | сеть или ограничения портала | повторите позже; если повторяется — проверьте нагрузку портала |
| После обновления всё сломалось | в прод уехала плохая версия | `make prod-rollback TAG=<прошлый номер>` |

## Приложение А. Первая настройка сервера

Делается один раз. Предполагается, что на сервере уже работают `nginx-proxy` и
`acme-companion` (выдача сертификатов), а DNS-запись домена смотрит на этот сервер.

**1. Адрес приложения в GitHub.** «Settings → Secrets and variables → Actions →
Variables» → переменная `NUXT_PUBLIC_SITE_URL` со значением вашего домена.
Значение попадает внутрь сборки, поэтому при смене домена нужна пересборка.

**2. Файлы на сервере.** Нужны ровно три файла из репозитория:

```bash
mkdir -p /home/bitrix/convert-bbocode-md && cd /home/bitrix/convert-bbocode-md
RAW=https://raw.githubusercontent.com/bx-shef/app-convert-bbocode-md/main
for f in docker-compose.prod.yml Makefile .env.prod.example; do
  curl -fsSL -o "$f" "$RAW/$f"
done
cp .env.prod.example .env.prod        # вписать домен и почту для сертификата
make init-network                     # общая сеть proxy-net, если её ещё нет
```

**Доступ к образу.** После первой сборки образ появляется в реестре GHCR
(хранилище образов при GitHub). Дальше два варианта:
- сделать пакет публичным: «Code → Packages → app-convert-bbocode-md →
  Package settings → Change visibility → Public» — тогда сервер тянет образ без входа;
- оставить приватным — тогда на сервере нужен `docker login ghcr.io`
  (логин GitHub, пароль — токен доступа с правом `read:packages`).

**3. Первый запуск.**

```bash
make up        # забрать образ и запустить
make ps        # состояние: ожидаем "Up … (healthy)"
make logs      # журнал, если что-то не так
```

**Автообновление.** На сервере работает общий Watchtower (один на хост, его
поднимает соседний проект): он раз в несколько минут подтягивает свежий образ и
перезапускает контейнер. Поэтому обычное обновление руками запускать не нужно —
команды `make up` и `make prod-redeploy` остаются для первого запуска и отката.
Важно: **второй Watchtower на том же сервере поднимать нельзя** — они конфликтуют.
Подробности и грабли — в
[гайде соседнего проекта](https://github.com/bx-shef/currency-converter/blob/main/docs/AI_DEPLOY_GUIDE.md).

**Проверка вручную, если нужна:**

```bash
docker ps --filter name=app-convert-bbocode-md      # контейнер healthy
curl -I https://ваш-домен/                          # ожидаем ответ 200
scripts/smoke.sh https://ваш-домен                  # страница + заголовки безопасности
```

## Приложение Б. Разработка на своей машине

Bitrix24 пускает в iframe только `https`, поэтому локальный сервер нужно вывести
наружу через туннель (ngrok, cloudflared).

```env
# .env
NUXT_PUBLIC_SITE_URL=https://ваш-туннель.ngrok.app
NUXT_ALLOWED_HOSTS=ваш-туннель.ngrok.app
```

```bash
pnpm install
pnpm dev        # http://localhost:3000
```

Дальше — как в шагах 3 и 4, но зарегистрируйте **отдельное** приложение в портале
(рядом с рабочим, чтобы не мешать друг другу). Кнопка dev-версии в чате помечена
приставкой `dev`, чтобы не перепутать.
